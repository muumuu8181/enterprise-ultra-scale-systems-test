# Security & AML

## 1. 脅威モデル（STRIDE分析）

本システムのセキュリティリスクを網羅的に分析し、対策を講じるためにSTRIDEモデルを採用しています。

| 脅威カテゴリ | 具体的脅威 | 対策 |
|---|---|---|
| **Spoofing** (なりすまし) | 第三者が正規ユーザーのJWTトークンを窃取してアクセスする。 | ・トークンの署名検証<br>・短い有効期限の設定<br>・JTI（ID）によるブラックリスト管理<br>・MFA（多要素認証）の強制 |
| **Tampering** (改ざん) | 悪意のある管理者がDB上の取引履歴や監査ログを書き換える。 | ・監査ログのハッシュチェーン記録（改ざん検知）<br>・Write-Once-Read-Many (WORM) ストレージの利用<br>・DBアクセス権限の分離 |
| **Repudiation** (否認) | ユーザーが「自分はこの取引を行っていない」と主張する。 | ・全ての操作に対する監査ログの記録（IP、タイムスタンプ、User-Agent）<br>・電子署名の利用（重要な取引） |
| **Information Disclosure** (情報漏洩) | 攻撃者がDBダンプを取得し、顧客の個人情報や口座情報を盗み見る。 | ・保存データの暗号化（AES-256-GCM）<br>・通信経路の暗号化（TLS 1.3）<br>・個人情報のマスキング表示<br>・最小権限の原則（Need-to-Know） |
| **Denial of Service** (サービス拒否) | 大量のAPIリクエストを送信し、システムをダウンさせる。 | ・レートリミッティング（Redis Token Bucket）<br>・Web Application Firewall (WAF) の導入<br>・オートスケーリング構成 |
| **Elevation of Privilege** (権限昇格) | 一般ユーザーが管理者APIを実行したり、他人の口座を操作する。 | ・RBAC（ロールベースアクセス制御）の徹底<br>・水平権限昇格のチェック（リソース所有者の確認）<br>・入力値バリデーションの強化 |

## 2. AML検知ルール詳細

マネーロンダリング（資金洗浄）およびテロ資金供与を防止するため、以下のルールに基づいて取引を監視します。

- **Rule 001: 高額現金取引 (Large Cash Transaction)**
  - **条件**: 1回あたり 200万円（または相当額）以上の現金入出金、または為替取引。
  - **アクション**: 自動的に「疑わしい取引報告書（STR）」の下書きを作成し、コンプライアンス担当者に通知。

- **Rule 002: 短期間の頻繁な送金 (Structuring / Smurfing)**
  - **条件**: 24時間以内に同一口座へ向けて、または同一口座から 3回以上の送金が行われ、その合計額が閾値（例: 50万円）を超える場合。
  - **アクション**: 「要確認（Flagged）」ステータスを設定し、一時的に取引を保留または監視対象に追加。

- **Rule 003: 制裁リスト照合 (Sanctions Screening)**
  - **条件**: 送金人、受取人、または関係者が、OFAC（米国財務省外国資産管理室）や国連の制裁リスト、PEPs（重要な公的地位にある者）リストに合致する場合。
  - **アクション**: 取引を**即時ブロック**（Rejected）し、AML担当者へ緊急アラートを送信。

- **Rule 004: 異常な急増 (Sudden Spike)**
  - **条件**: 過去3ヶ月の平均入金額の 10倍以上の入金があった場合。
  - **アクション**: 「要確認（Flagged）」フラグを立て、資金源の確認（SoF: Source of Funds）を要求するタスクを生成。
